OUT-OF-FOLD Predictions

How do we make sure that every comment is predicted by a model that has never seen it during training? This visual guide follows the complete process: creating folds, training one model per fold, routing each comment to the correct model, and collecting the final OOF predictions.

01
Stage One · Training

Build the Folds. Train the Models.

First, comments are grouped by product. Then the groups are distributed across five folds. Each model is trained on four folds and evaluates only the one fold left out.

▤

Comment Dataset

The valid, labeled comments prepared for the current prediction task.

More about the input

Each comment has an identifier, a product identifier, and a target label. Only rows valid for the current prediction head participate in its fold assignment.

→
▦

Group by Product ID

All comments belonging to the same product are kept together.

Why group by product?

This prevents comments from the same product from appearing in both the training and held-out partitions of a fold iteration.

→
⫶

StratifiedGroupKFold

Five folds are created while keeping product groups intact and attempting to preserve class proportions.

How does this splitter work?

Group constraint: a product group must stay in one fold. Stratification: the splitter tries to keep class distributions reasonably balanced across folds. Perfect balance is not guaranteed.

Collect All Held-Out Predictions

Each model contributes predictions for its own held-out fold. These five sets of predictions are then combined into one OOF dataset.

Fold 1 + Fold 2 + Fold 3 + Fold 4 + Fold 5 → OOF Dataset
▦

The Product-Level Isolation Rule

Suppose all comments from Product P are assigned to Fold 3. Then every comment from Product P is held out together. Model 3 is trained on Folds 1, 2, 4, and 5, so it has seen none of Product P's comments during training. This is how product-level leakage is prevented in this split design.

03
The Core Idea

What Makes a Prediction Truly OOF?

The important property is not simply that a prediction exists. It is that the model generating it did not train on that sample.

01

Held Out During Training

A comment belongs to exactly one validation fold in a given cross-validation run. Its corresponding model does not use it for fitting.

02

Predicted by Its Matching Model

A comment in Fold 3 receives predictions from Model 3, not from Model 1, Model 2, or a model trained on that comment.

03

Combined into One Dataset

Predictions from all held-out folds are collected. Each valid comment gets its own out-of-fold prediction record.

Technical notes and project-specific considerations

1. Probabilities are not necessarily a single confidence value. For a three-class classification task, the model can produce a probability for each class: p_recommended, p_no_idea, and p_not_recommended. These values typically sum to 1 for a standard multiclass probability output.

2. Maximum class probability can be used as a simple confidence score. For example, if the probabilities are 0.82, 0.12, and 0.06, the maximum probability is 0.82. However, this does not automatically mean that the model is well-calibrated or that the prediction has an 82% real-world probability of being correct.

3. Product grouping is applied during fold creation. The group identifier is product_id. All comments sharing a product ID must remain in the same fold. This is the key restriction that prevents the same product from appearing in both the training and held-out partitions of one iteration.

4. Stratification is an objective, not a guarantee of perfect balance. StratifiedGroupKFold attempts to preserve class proportions while respecting the group constraint. Some imbalance may remain, particularly when product groups are large or class distributions differ considerably between products.

5. Run the process separately for each prediction head when its fold assignment is separate. In this project, recommendation and rating-band tasks may have different valid rows and different fold assignments. If they use separate columns such as fold_rec and fold_band, each head must use its own fold-to-model mapping when generating OOF predictions.

6. The OOF dataset contains held-out predictions, not predictions from the model that trained on the same comment. This distinction is what makes OOF predictions useful for downstream analysis and training workflows that require predictions generated without in-sample exposure.

The Complete Logic

One Comment → One Matching Model → One OOF Record

For every valid comment, read its fold assignment, select the model that held that fold out during training, retrieve that model's probabilities for the comment, and store them in the OOF dataset. The result is a collection of out-of-training predictions: every comment is predicted by a model that did not train on it.
